## 1. 核心的動作原理 (Single Source of Truth)
- **SSoT の遵守**: 実装・設計の判断は、常に `docs/REQUIREMENTS.md`（要件）と `docs/DESIGN.md`（デザイン）を絶対的な正解として扱うこと。
- **勝手な改変の禁止**: ユーザーからの明示的な命令、または `notify_user` による合意なしに、設計書に反する実装を行わないこと。
- **コンテキストの優先順位**: 1. ユーザーの最新の指示, 2. 本ルールファイル, 3. `docs/` 配下のドキュメント。

## 2. 出力・コミュニケーション規約
- **使用言語**: すべての報告、計画、コミットメッセージは**日本語**で生成すること。
- **透明性の確保**: 重要な技術選定（ライブラリの追加など）が発生する際は、`notify_user` を用いて承認を得てから実行すること。
- **簡潔な要約**: `task_boundary` におけるサマリーは、完了したタスクを技術的に正確かつ簡潔に記述すること。

## 3. 開発運用ルール
- **Issue ベースの実行**: タスク開始前に必ず関連する GitHub Issue を確認し、進捗を `task.md` に反映させること。
- **テンプレートの活用**: Issue や Pull Request を作成する際は、`.github/` 配下に定義されたテンプレートを必ず使用し、構造化された情報を記述すること。
- **Git 運用**:
    - **ブランチ戦略**: 新しい機能の開発や修正を行う際は、必ず `main` ブランチから新しいブランチ（例: `feat/issue-1-design-system`）を作成して作業すること。
    - **コミットメッセージ**: 適切なプレフィックス（`feat:`, `fix:`, `docs:`, `style:`）を付与し、日本語で記述すること。
    - **リモート同期**: 意味のある単位で `git push` し、作業ブランチをリモートと同期させること。

## 4. 品質保証プロセス
- **自律的修復**: ビルドエラーや依存関係の欠損は、自律的に原因を特定し修正を試みること。
- **実機検証**: UI の変更を伴うタスクの完了前には、必ず `browser_subagent` を使用して `http://localhost:3000` での動作確認を行い、スクリーンショットを提示すること。
